# 4단계 일정 관리 검증

검증일: 2026-11-17. 로컬 단일 사용자 MVP, 일정과 기록은 독립 테이블이다.

## 최신 수정·재검증

- 일정 저장/삭제 중 부모의 새 일정·다른 일정 열기·페이지·새로고침을 잠가 이전 응답으로 새 초안이 닫히는 문제를 수정했다. 실패 후 입력은 유지하고 잠금은 해제한다.
- 다가오는 일정의 저장 완료 문구와 괄호 안 날짜를 제거했다. 일정 자체의 날짜와 조회 실패/재시도는 유지한다.
- 일기 검증 스크립트는 목록 응답 대기·마지막 페이지 판정을 보완했다. 200ms 지연 응답과 테스트 일기 5개를 추가해 다중 페이지 탐색 후 정리한다.
- 최종 프론트 lint/build, verify-stage3-ui.cjs, verify-schedules-ui.cjs, verify-schedule-editor-ui.cjs 통과. 편집 잠금 검증은 모의 API를 사용하며 실제 DB 쓰기가 없다. 백엔드는 앞선 test --rerun-tasks 8개 통과 결과를 사용한다.
- AI 중단/DB 재시작 검증은 최초 4단계 실행 이력이며 UI 수정 후 반복하지 않았다. 해당 런타임 스크립트의 목록 요청은 현재 홈 전용 API 계약에 맞춰 갱신했다.

## 이후 사용자 요청으로 변경한 범위

최신 제거 검증: 프론트 lint/build, 백엔드 test/bootJar 통과. 백엔드 로컬 컨테이너 재빌드·교체 후 verify-schedules-ui.cjs 통과(제거 조건 400, 다가오는 일정 CRUD·상태·실패 처리·390px). DB 스키마와 기존 일정 데이터는 변경하지 않았다. 이번 수정에서는 AI 중단/DB 재시작 검증을 반복하지 않았다.

일정 관리 UI와 기간·상태별 조회를 제거했다. GET /api/schedules는 서울 오늘~6일 후 PLANNED만 조회하며 page/size만 받는다. start/end/status 파라미터는 빈 값도 400이다. 다가오는 일정 및 일정 CRUD/상태 변경은 유지한다. 아래 기간별 관리 검증은 제거 전 이력이다. 검증 스크립트는 현재 UI/API에 맞춰 수정했다.

## 구현

- Flyway V2 schedules 테이블과 상태/날짜 인덱스. 기존 V1은 변경하지 않았다.
- Schedule Entity/Repository/Service/DTO/Controller, 기록·일정 공통 오류 응답.
- 일정 등록·상세·수정·상태 변경·영구 삭제. 일정명·날짜 필수, 시간·장소·메모 선택.
- 서울 현지 시간 HH:mm, 시간 미정 허용. 상태는 예정·완료·취소 중 사용자가 변경한다.
- 홈에 오늘~6일 후 PLANNED 목록과 페이지 처리. 기간·상태별 관리 UI/API는 이후 제거했다.
- 저장 중 중복 요청 차단, 실패 시 초안 보존, 저장 성공과 목록 실패 분리, 삭제 확인/취소/실패 처리.

API 테스트: 시간 미정·빈 선택값 정리·줄바꿈·과거 날짜, CRUD/상태, 404, 날짜 경계(오늘/6일 후 포함, 전날/7일 후 제외), 00:00/23:59와 동률 ID 정렬, 시간 미정 후순위, 페이지 처리, 잘못된 시간/날짜/필드 길이/상태/조회 조건 거부.

UI 테스트: 시간 미정 생성, POST 실패 시 입력 유지, 저장 성공 후 목록 실패/다시 조회, 새로고침 유지, 시간·장소·메모·완료/취소 상태 변경, 날짜를 과거로 이동하고 관리 기간에서 조회, 삭제 취소/실패/성공, 390px 가로 넘침 없음, 브라우저 오류 없음. 생성 일정은 finally에서 삭제한다.

실제 실행 검증: AI 서버를 중단한 상태에서 일정 저장·조회·상태 변경 성공. 실제 MySQL의 7일 경계·시간 정렬·상태 제외 확인. MySQL과 백엔드 재시작 후 원문·시간·UTC 작성/수정 시각이 등록 응답과 동일함을 확인했다. 생성한 테스트 일정은 삭제했고 AI를 실행 상태로 복구했다.

## 발견하여 수정한 문제

- LocalTime을 JDBC가 JVM/UTC로 변환하면 자정 일정의 정렬이 뒤집혔다. LOCAL_TIME JDBC 타입을 지정하여 서울 현지 시각 그대로 저장하도록 수정했다. H2와 실제 MySQL의 자정/23:59 조회·정렬을 확인했다.
- MySQL DATETIME(6)와 등록 응답의 나노초 정밀도가 달랐다. 일정 작성/수정 시각을 마이크로초로 맞춰 DB 조회 응답과 일치하도록 수정했다.
- 상태 select에 정확한 접근성 이름을 부여하여 상태 선택을 검증했다.

## 범위와 한계

- 통합 캘린더의 일정 표시와 미래 날짜 선택 등록·날짜별 조회/수정/삭제/상태 변경은 5단계다. 홈은 예정 일정 확인용이며 현재 캘린더는 기록만 표시한다.
- AI 약속 준비·로그인·반복 일정·알림·외부 연동은 구현하지 않았다.
- 여러 탭 동시 수정은 마지막 저장 반영. 날짜 기본값은 화면을 다시 열어 갱신하며 자정 자동 갱신 타이머는 없다.
- API와 재실행 명령은 MINIMUM_DESIGN.md 7절과 scripts/verify-schedules-*.cjs를 참고한다. 브라우저 스크립트는 PLAYWRIGHT_MODULE_PATH로 기존 임시 Playwright 경로를 전달한다.
