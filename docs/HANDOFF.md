## 구현과 정책

- records: 메모·일기 CRUD, 일기 선택 제목, 서울 기준 오늘 이전 경험 날짜, 하루 여러 건, 제목/본문/날짜 변경 시 버전 증가/PENDING. 동일 값은 버전 유지.
- 기록 목록: 최신 경험 날짜 → 작성 시각 → ID 내림차순. 전체/메모/일기 및 페이지. 일반 검색 입력과 keyword/from/to 요청은 제거했고 해당 요청은 400이다.
- 캘린더: start/end 양끝 포함 월별 기록 조회. 둘 다 필수, type과 동시 지정 거부. 기록만 표시한다.
- schedules: 일정명·날짜 필수, 시간·장소·메모 선택. 과거/미래·시간 미정 허용. 상태는 사용자 지정 예정/완료/취소이며 자동 변경하지 않는다.
- 홈 일정: 서울 오늘~6일 후의 PLANNED만. 날짜 → 시간 있음/시간순 → ID 오름차순. 일정 관리에서 다른 기간·완료/취소도 조회·수정·삭제한다.
- 저장 실패 시 입력 보존, 요청 중 중복 저장 차단, 삭제 확인 후 물리 삭제. 저장 성공과 목록 조회 실패를 분리한다. 여러 탭 수정은 마지막 저장 반영.
- MySQL 원본 저장·조회에 AI 호출은 없다. PENDING은 원문 저장 성공·검색 준비 전이다. 일정은 벡터화하지 않는다.
- Flyway V1 records / V2 schedules 적용, JPA validate. 적용한 SQL은 수정하지 않는다. 일정 LocalTime은 직접 JDBC 매핑, 작성/수정 시각은 UTC 마이크로초.

## 검증 근거

- frontend: npm.cmd run lint / npm.cmd run build 통과.
- backend: gradlew.bat test bootJar --no-daemon 통과. 총 8개(컨텍스트 1, 기록 API 4, 일정 API 3), H2 사용.
- 실제 MySQL: Flyway V1/V2 success=1, records/schedules 존재. H2 테스트와 별도로 확인했다.
- Edge: 메모/일기/일정 CRUD, 실패 입력 보존·재조회, 상태·날짜 변경, 삭제 확인, 390px 가로 넘침 없음. scripts/verify-query-ui.cjs로 기존 필터/캘린더 회귀 검증 통과.
- 일정 실행 검증: scripts/verify-schedules-ui.cjs 및 verify-schedules-runtime.cjs 최종 통과. AI 중단 중 일정 저장·조회, 7일 경계·시간 정렬, MySQL/백엔드 재시작 후 원문·시간·UTC 시각 유지 확인.
- 생성한 일정 검증 데이터 잔여 0건. AI 복구, 6개 서비스 running 및 MySQL healthy 확인. 서비스 실행 상태만으로 AI 업무 기능 완료라고 판단하지 않는다.
- 발견한 시간 정렬의 JVM/UTC 변환과 DB 시각 정밀도 차이는 수정 후 재검증했다.
- 상세 결과: [2단계](STAGE2_CHECK.md), [4단계](STAGE4_CHECK.md), [초기 환경](ENVIRONMENT_CHECK.md). 전체 재검증은 문서 수정마다 반복하지 않으며 새 변경에 맞는 검증을 수행한다.
