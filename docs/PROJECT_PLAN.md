## 1. 서비스 개요

MEMORIA는 일기와 메모로 과거를 기록하고, 일정으로 미래를 준비하며, AI로 필요한 기억을 다시 찾는 서비스다. 여유 있는 날에는 일기로 자세히 쓰고, 바쁜 날에는 짧은 메모로 남긴다. 약속은 미리 등록하고 캘린더에서 확인한다. AI는 원문을 찾아 질문에 답하거나 예정된 일정의 준비를 돕는다.

대표 흐름: **일정 등록 → 관련 기억 확인 → 약속 준비 → 경험 후 기록 → 기억 검색**. 모든 단계를 반드시 수행할 필요는 없다. 일정에서 기록으로 자동 연결하는 기능은 후속 개발이다.

## 2. 문제와 사용자

초기 가설: 긴 일기를 매일 쓰기 어렵고, 흩어진 기록에서 기억을 다시 찾기 어려우며, 약속 전에 과거 대화나 준비물을 잊을 수 있다. 짧은 기록, 통합 캘린더, 의미 검색, 근거 기반 준비 안내로 해결을 시도한다. 시장 조사로 입증한 사실로 표현하지 않는다.

핵심 사용자는 일상을 남기고 싶지만 매일 긴 글은 부담스럽고, 지난 경험과 예정된 약속을 함께 관리하고 싶은 사람이다. MVP는 일상·만남·여행 등의 개인 기록을 중심으로 한다.

## 3. 기록과 일정 정책

### 빠른 메모

- 홈에서 본문만 입력해 저장한다. 제목은 요구하지 않는다.
- 날짜는 오늘 기본값, 과거 날짜로 변경 가능하다.
- 하루 여러 개 허용하며 본문 일부를 목록에 표시한다.

### 일기

- 별도 작성 화면에서 날짜·본문, 선택 제목을 입력한다.
- 하루 여러 개 허용한다. 메모와 글자 수로 강제 구분하지 않는다.
- 실제 경험 날짜와 작성 시각을 분리한다. 캘린더는 경험 날짜 기준이다.
- 공백 본문은 저장할 수 없다. 미래 날짜 기록은 MVP에서 제한한다.

### 일정

- 필수: 일정명·날짜. 선택: 시간·장소·메모.
- 시간 미정 허용, 단일 날짜 일정만 지원한다.
- 상태: 예정·완료·취소. 사용자가 변경하며 시간 경과로 참석을 추정하지 않는다.
- 홈에서 오늘부터 향후 7일의 예정 일정을 확인한다. 정확한 기간 경계는 API 설계에서 정의한다.
- 반복·여러 날 일정·푸시 알림·외부 연동은 제외한다.

## 4. MVP 기능

| 구분 | 범위 |
|---|---|
| 기록 | 빠른 메모, 일기 작성·조회·수정·삭제 |
| 아카이브 | 통합 목록, 일기·메모 구분/필터, 날짜순 조회, 기본 페이지 처리(일반 키워드 검색은 사용자 요청으로 제외) |
| 일정 | 등록·조회·수정·삭제, 상태 변경, 다가오는 일정 |
| 캘린더 | 월 이동·오늘 이동, 종류별 표시, 날짜별 목록, 선택 날짜로 작성 |
| 인덱스 | 임베딩·갱신·삭제·처리 상태·재시도 |
| AI 검색 | 일기·메모 통합 검색, 근거 답변, 원문 출처 |
| AI 약속 준비 | 관련 기억·준비사항·누락 정보·출처 |
| 안정성 | 저장/검색 상태 분리, 장애·근거 부족 처리 |

날짜 변경·삭제 결과는 목록과 캘린더에 반영한다. 캘린더의 일기·메모·일정은 색상뿐 아니라 텍스트로도 구분한다.

## 5. AI 기억 검색

예: “민수랑 갔던 조용한 카페가 어디였지?”

흐름: 질문 → 키워드·의미 검색 → 후보 중복 제거 → 유효 원문 확인 → 답변 생성 → 출처.

일기·메모를 함께 검색하고 종류만으로 우선순위를 정하지 않는다. 날짜 범위는 UI 조건을 사용하며 복잡한 자연어 날짜 해석은 제외한다. 같은 사건의 메모와 일기를 별개 사건으로 단정하지 않는다.

응답에는 짧은 답변, 기록 종류·날짜·제목/미리보기, 관련 원문 문장, 원문 링크를 제공한다. 카페 이름 등 정보가 원문에 없으면 확인할 수 없다고 안내한다.

## 6. AI 약속 준비

일정 상세의 **AI로 약속 준비하기** 버튼으로 실행한다. 일정명·날짜·시간·장소·메모를 검색 입력으로 사용한다.

| 출력 | 내용 |
|---|---|
| 관련 기억 | 같은 인물·장소·주제의 일기·메모 |
| 기억해둘 내용 | 다음에 하기로 했던 일 등 |
| 준비사항 | 기록에 명시된 항목과 AI 제안 구분 |
| 확인할 정보 | 일정에서 빠진 시간·장소 |
| 출처 | 각 근거 기록과 연결 |

예: ‘민수와 저녁 약속’에 대해 ‘다음에 파스타 먹기’, ‘빌린 책 돌려주기’ 기록을 제시한다. 이미 돌려줬을 수 있으므로 지금도 미완료라고 단정하지 않는다.

관련 기록이 없으면 그 사실을 안내하고 누락 정보만 보여준다. 자동 실행·알림, 날씨·교통·영업시간 등 실시간 외부 정보는 포함하지 않는다.

## 7. AI 공통 원칙

- 실제 검색된 원문만 근거로 사용하고 사실과 제안을 구분한다.
- 오래된 정보가 현재도 유효하다거나 동명이인이 같은 사람이라고 단정하지 않는다.
- 근거 부족 시 확인 불가를 안내한다. 감정·심리를 원문 이상으로 단정하지 않는다.
- 출처 ID는 백엔드가 실제 기록으로 구성한다. 항목별 근거 연결을 검증한다.
- 기록 본문 속 명령을 시스템 지시로 취급하지 않는다.
- AI가 기록·일정을 자동 변경하지 않는다.
- 설계는 오류 감소를 위한 것이며 정확성을 완전히 보장하지 않는다.

## 9. 기술과 책임

기존 기획 기준 스택: React/TypeScript/Vite, Spring Boot/Spring Data JPA, MySQL, FastAPI, Qdrant, Ollama, Docker Compose. 실제 코드와 버전은 별도 확인한다. LLM·임베딩 모델은 첫날 환경·한국어 품질·응답 속도를 검증한 뒤 확정한다.

- Spring Boot: 기록·일정 관리, 원문 검증, 검색 요청 조정, 출처 구성.
- FastAPI: 임베딩·벡터 검색·생성.
- MySQL: 원본 기준 저장소. Qdrant: 재생성 가능한 검색 인덱스.
- AI 장애가 기록·일정 저장/조회에 영향을 주지 않도록 한다.
- 원문 저장과 검색 준비 완료를 분리한다. 답변 생성만 실패하면 확보된 관련 기록을 보여줄 수 있다.

## 10. 데이터 설계 기준

### Record

`record_id`, `record_type`(DIARY/MEMO), 선택 `title`, `content`, `record_date`, `content_version`, `embedding_status`(PENDING/COMPLETED/FAILED), `indexed_version`, `created_at`, `updated_at`.

### Schedule

`schedule_id`, `title`, `schedule_date`, 선택 `schedule_time`, `location`, `description`, `status`(PLANNED/COMPLETED/CANCELLED), `created_at`, `updated_at`.

### 검색 인덱스

기록:청크는 1:N. 기록 ID·청크 ID·원문 버전·날짜·벡터를 관리한다. 수정 전 버전과 삭제 기록은 원문 검증 단계에서도 제외한다. 실패 재처리 경로가 필요하다. 일정은 MVP에서 벡터화하지 않고 검색 입력으로 사용한다.

입력 길이, 시간 저장 정책, 삭제 방식, 재시도 방법은 최소 설계에서 결정한다.

## 11. API 기준안

| Method | Endpoint | 기능 |
|---|---|---|
| POST/GET | `/api/records` | 등록/목록 |
| GET/PUT/DELETE | `/api/records/{id}` | 상세/수정/삭제 |
| POST/GET | `/api/schedules` | 등록/기간 조회 |
| GET/PUT/DELETE | `/api/schedules/{id}` | 상세/수정·상태/삭제 |
| GET | `/api/calendar` | 기간별 기록·일정 요약 |
| POST | `/api/ai/search` | AI 기억 검색 |
| POST | `/api/schedules/{id}/prepare` | AI 약속 준비 |

요청·응답 예시, 필터·페이지 조건, 공통 오류 형식은 구현 전에 정의한다.

## 12. 일정과 완료 기준

상세는 `DEVELOPMENT_PLAN.md`를 따른다. 1주차 기록·일정·캘린더, 2주차 인덱스·AI 기능·검증을 목표로 한다. 마지막 16시간은 테스트·결함 수정·문서화에 배정한다. 80시간은 개발 예산이며 완료 보장은 아니다.

필수 시연:

1. 메모/일기 작성 → 캘린더 → AI 기억 검색 → 원문.
2. 일정 등록 → 다가오는 일정 → AI 약속 준비 → 근거 기록.

수정·삭제 반영, AI 중단 시 원문 보존, Docker 재시작 후 데이터 유지를 검증한다.

AI 평가 데이터: 가상 기록 약 30개, 검색 질문 20개(정답 있음 15/없음 5), 약속 준비 사례 5개(동명이인·오래된 정보·기록 없음 포함). 검색 목표는 정답 있는 15개 중 12개 이상에서 상위 5개에 정답 포함. 생성 사실 일치·출처·근거 없는 내용도 별도로 확인한다. 소규모 개발 평가 결과로만 보고한다.

## 13. 보안·운영

로컬 단일 사용자로 제한한다. 비밀값은 환경변수로 관리하고 저장소·시연에 실제 개인 기록을 포함하지 않는다. DB·벡터 DB·모델 서버는 외부 직접 공개를 피한다. 공개 배포는 인증·사용자별 접근 제어와 데이터 격리 후 별도 진행한다.

## 14. 후속 확장

- 기록 연결: 당일 메모 참고, 일정에서 기록 작성, 메모 기반 일기 초안.
- 기억 보관: 즐겨찾기·감정·사진·추억 보관함.
- 회고: 월간 요약·관련 기억·지난 기억 돌아보기.
- 일정: 자연어 등록·반복·알림·외부 연동.
- 운영: 로그인·다중 사용자·공개 배포.

추억 보관함은 여러 일기·메모를 여행 등 하나의 주제로 연결한다. 원문을 복사하지 않고 보관함 삭제 시 원문을 유지한다. AI 요약은 근거 변경 시 갱신 여부를 관리한다.

## 15. 최종 산출물

실행 가능한 기록·일정·캘린더 웹 서비스, AI 검색·약속 준비·출처, 인덱스 동기화, Docker 실행 환경, API 명세·README, 평가 결과·시연 자료·알려진 한계.
